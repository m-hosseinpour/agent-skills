# Discipline Wording Without Manipulation

Use when a legitimate quality or safety practice is repeatedly skipped under pressure. The aim is a useful decision at the right time, not maximizing obedience. This guide replaces the inherited persuasion recipes; it makes no claim that persuasion-study compliance rates predict skill quality or loading.

## Start With the Failure

Identify what was skipped, what harm followed, and which instruction the agent actually saw. Check whether the cause was missing metadata, an unread reference, ambiguity, unavailable tools, a bad rule, or a conflict with higher-priority instructions. Emphatic wording cannot fix all of these.

Choose the least forceful wording that makes the legitimate requirement clear:

| Need | Better wording | Why |
| --- | --- | --- |
| Verification before a claim | “Before claiming the patch is verified, run the relevant available check and read its result; if blocked, report what remains unverified.” | Ties the action to a claim and permits honest limits |
| Preserve user data | “Do not overwrite existing output. Select a new destination or ask before replacing it.” | Protects a real boundary without inventing permission |
| Avoid unsupported schemas | “Use current documentation or an authorized request to establish the response shape before coding its consumer.” | Names the evidence and the dependent decision |
| Adaptable report shape | “Use this structure when a full handoff is requested; a brief answer can stay in chat.” | Keeps useful consistency without ceremony |

## Firm Rules Need Real Bounds

State the trigger, action, reason when non-obvious, and exception or blocked-state response. Prefer “when X, do Y before Z” over a vague recommendation when order matters. Reserve absolute prohibitions for genuine boundaries such as unapproved destructive actions or fabrication.

Do not require skill announcements, todos, fixed test counts, or user approvals just to manufacture commitment. They are appropriate only when they solve a concrete coordination, tracking, or decision need. Do not imply urgency, credentials, consensus, psychological mechanisms, or guaranteed compliance without evidence.

Do not use guilt, threats, flattery, or “if you did not use this skill, you failed” as a substitute for explaining relevance. A skill must remain subordinate to user constraints and higher-priority instructions. Authorized emergency containment, asking for material permission, or declining unavailable work can be correct even when a preferred workflow cannot be completed.

## Examples Must Respect the Same Constraints

A warning not to delete user work is undermined by an example ordering deletion of already-written code for missing test-first order. Explain how to obtain useful missing verification within project norms instead; no example grants destructive authorization.

Likewise, “always run the full suite” is wrong when the relevant suite is known to fail unchanged or the project has no framework. Ask for relevant evidence using existing checks and disclose limitations rather than expanding the task unasked.

## Evaluate the Decision

Use a realistic pressured scenario and a legitimate exception. Compare decisions and outputs, not whether the evaluator recites a rule or acknowledges temptation. If stronger wording improves one example but blocks valid behavior, revise the boundary instead of adding more prohibitions.

The original guide cited human persuasion literature and a study about getting AI to comply with objectionable requests. That is not evidence of better safe task outcomes, automatic skill selection, or a universal model psychology. No numeric claim from that reference is retained here.
